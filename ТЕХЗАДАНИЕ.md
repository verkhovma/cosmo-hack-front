## 1. Краткое описание задачи

Разработать веб-сервис для проектирования спутниковой группировки и оценки доступности связи в северных районах. Пользователь загружает параметры группировки, выбирает этап развёртывания, изменяет конфигурацию и проверяет работу сети при отказах аппаратов. Сервис рассчитывает покрытие наземных пунктов, строит маршруты передачи данных и позволяет сравнить результаты нескольких вариантов.

## 2. Полное описание и проблематика

Планируется развёртывание группировки из **48 спутников** на орбитах высотой **550 км**. Запуск выполняется в **три очереди по 16 аппаратов** с интервалом в три месяца. Группировка должна обеспечивать связь между северными наземными пунктами и шлюзом выхода в наземную сеть. В течение полёта меняются взаимное расположение спутников и доступность наземных пунктов; отдельные аппараты могут временно выходить из строя.

При выборе конфигурации необходимо учитывать одновременно покрытие территории и возможность доставить данные до наземного шлюза. Наличие спутника над пунктом ещё не обеспечивает сквозной маршрут. Состав доступных связей меняется во времени, а отказ одного аппарата может затронуть сразу несколько направлений передачи. На ранних этапах развёртывания эти ограничения особенно заметны.

Для принятия проектных решений требуется сопоставлять варианты на одном периоде расчёта: определять продолжительность перерывов, находить уязвимые участки сети и оценивать, как изменения конфигурации сказываются на доступности связи.

## 3. Цель, пользователь, целевой показатель

Разработать сервис, с помощью которого **инженер-проектировщик** сможет выбрать конфигурацию группировки, оценить её устойчивость и обосновать рекомендации по развёртыванию.

Целевой ориентир — **доступность связи не менее 90% расчётного времени для каждого наземного пункта**. Результаты должны показывать фактическую достижимость этого уровня в выбранных условиях.

## 4. Функциональные требования

### 4.1. Подготовка и изменение конфигурации

Сервис загружает сценарий из предоставленного набора и отображает состав группировки, орбитальные плоскости, наземные пункты и параметры расчёта. В интерфейсе предусмотрены:

- выбор очереди запуска;
- изменение ориентации плоскостей (RAAN) и фазирования аппаратов (phase_deg);
- добавление периодов недоступности выбранных спутников;
- сохранение варианта и возврат к нему для сравнения.

### 4.2. Моделирование покрытия и сети

На каждом шаге расчёта сервис определяет положения активных спутников, видимость наземных пунктов и доступные межспутниковые связи. Пользователь может просмотреть состояние сети в выбранный момент времени, определить спутники, обслуживающие наземный пункт, и увидеть периоды отсутствия связи.

### 4.3. Маршрутизация и реакция на отказы

Для выбранного наземного пункта строится маршрут до доступного шлюза через спутниковую сеть. Маршрут пересчитывается при изменении положения аппаратов и их доступности. Для периода без маршрута сервис показывает причину:

- отсутствие видимого спутника;
- разрыв межспутниковой сети;
- отсутствие контакта со шлюзом или его недоступность.

Команда самостоятельно выбирает способ поиска и обновления маршрутов.

### 4.4. Сравнение вариантов и рекомендации

Сервис сопоставляет **как минимум два сохранённых варианта** по доступности связи, продолжительности перерывов и характеристикам маршрутов. На основе сравнения команда предлагает конфигурацию и объясняет её преимущества для заданных наземных пунктов. В расчётах необходимо рассмотреть полную группировку, промежуточный этап развёртывания и сценарий отказов.

Дополнительно могут быть реализованы: автоматический подбор конфигурации, поиск наиболее уязвимых аппаратов, анализ резервных путей, сравнение стратегий маршрутизации и дополнительные средства сценарного анализа.

## 5. Требования к интерфейсу

Основной пользовательский сценарий: выбрать или загрузить проект → настроить конфигурацию → запустить расчёт → просмотреть состояние сети → сравнить результаты. Параметры группировки и периоды отказов редактируются в экранных формах.

- **Карта/схема:** спутники, наземные пункты, доступные связи и выбранный маршрут. Подписи позволяют определить аппарат и его состояние.
- **Временная шкала:** переход к нужному моменту расчёта. Диаграмма доступности показывает интервалы связи и перерывы по каждому наземному пункту.
- **Сравнение вариантов:** видны изменённые параметры, итоговые показатели и различия между результатами.
- **Обработка ошибок:** при загрузке некорректного файла сервис сообщает, какие данные необходимо исправить. Для повторного эксперимента предусмотрены сброс изменений и новый запуск.

## 6. Базовые сценарии проверки

1. **Полная группировка.** Загрузить `01_full_constellation.json`, выполнить расчёт, выбрать наземный пункт и просмотреть маршрут в нескольких моментах времени.
2. **Этап развёртывания.** Переключить очередь запуска с третьей на первую и сравнить доступность связи и продолжительность перерывов.
3. **Отказ аппарата.** Выбрать спутник текущего маршрута, задать период его недоступности и повторить расчёт. Сервис показывает изменение маршрута или возникший перерыв.
4. **Изменение проекта.** Изменить ориентацию или фазирование одной плоскости, сохранить вариант и сопоставить с предыдущим результатом. Изменённый сценарий можно выгрузить и повторно загрузить.

## 7. Ожидаемый результат и технические требования

**Ожидаемый результат:** развёрнутый веб-сервис с работающим расчётом, маршрутизацией и сравнением конфигураций. Команда предоставляет ссылку и необходимые доступы, исходный код в репозитории, инструкцию запуска и презентацию решения. Результаты расчёта и использованные параметры должны выгружаться из сервиса.

В презентации необходимо показать выбранный подход, сравнение конфигураций, работу при отказах и рекомендации по проекту. Продолжительность защиты — **до 5 минут**. Во время проверки жюри сможет загрузить дополнительный сценарий того же формата и изменить параметры через интерфейс.

**Технические требования:** технологии frontend, backend и хранения данных команда выбирает самостоятельно. Веб-сервис должен быть доступен жюри через браузер до завершения проверки. Инструкция в репозитории должна содержать команды запуска, зависимости и порядок работы с сервисом. Оценка проводится по разделу 18. Отраслевые эксперты рассматривают проектные решения, анализ устойчивости и удобство сервиса. Технические эксперты проверяют расчёты, маршрутизацию, работу с новыми входными данными и качество реализации.

Один файл JSON содержит один проект группировки и условия его расчёта. Для начала работы используйте `01_full_constellation.json`. Сервис загружает файл, отображает параметры и рассчитывает состояние сети на заданном периоде. Изменение настроек в интерфейсе создаёт новый вариант проекта.

## 11. Конфигурация: design

`launch_stage` — номер выбранной очереди запуска: 1, 2 или 3. В расчёте участвуют спутники, у которых `launch_batch` не превышает `launch_stage`, с учётом периодов их недоступности.

| Объект и поле | Назначение |
|---|---|
| `planes[].id` | Уникальный идентификатор орбитальной плоскости |
| `planes[].raan_deg` | Ориентация плоскости: прямое восхождение восходящего узла, градусы от 0 включительно до 360 исключительно |
| `planes[].phase_deg` | Общий сдвиг положения аппаратов вдоль орбиты этой плоскости, градусы в том же диапазоне |
| `satellites[].id` | Уникальный идентификатор спутника |
| `satellites[].plane_id` | Идентификатор плоскости из `planes` |
| `satellites[].slot_deg` | Начальное угловое положение спутника внутри плоскости, градусы. К нему прибавляется `phase_deg` |
| `satellites[].launch_batch` | Очередь запуска спутника: 1, 2 или 3 |

В полной конфигурации заданы три плоскости по 16 аппаратов. RAAN определяет ориентацию плоскости, `phase_deg` — положение спутников вдоль неё. При сравнении проектов пользователь меняет эти параметры и выбранную очередь запуска; состав файлов позволяет сохранять весь вариант целиком.

## 12. Наземные пункты и периоды недоступности

Каждый элемент `ground_sites` содержит `id`, `name`, `role`, `lat_deg` и `lon_deg`. `role` принимает значение `client` для обслуживаемого пункта или `gateway` для шлюза. Широта — от −90 до 90°, долгота — от −180 до 180°. Идентификаторы наземных пунктов и спутников должны различаться.

Событие `failures` задаётся полями `satellite_id`, `start_s`, `end_s`. Для `gateway_outages` используются `gateway_id`, `start_s`, `end_s`. Начало интервала включается, конец исключается. Пересекающиеся интервалы объединяются по смыслу недоступности. Например, период `[21 600; 43 200)` действует с шестого до двенадцатого часа.

## 13. Правила расчёта

Модель использует круговые орбиты и сферическую Землю. Положение спутников рассчитывается непрерывно, состояние связей проверяется на заданной сетке времени. Для наземной линии применяется единый порог угла возвышения. Межспутниковый контакт определяется дальностью и отсутствием пересечения линии связи с Землёй.

### 13.1. Координаты спутников

Константы: радиус Земли `R = 6371 км`; гравитационный параметр `μ = 398600,435507 км³/с²`; период вращения Земли `T = 86164,09054 с`. Для высоты `h` радиус орбиты `r = R + h`, угловая скорость `n = √(μ/r³)`. Перед расчётом углы переводятся из градусов в радианы.

Пусть `Ω` — `raan_deg` плоскости, `i` — `inclination_deg`, `u(t) = slot_deg + phase_deg + n·t` (углы в сумме переведены в радианы). Координаты спутника в инерциальной системе:

```text
x = r·(cos Ω·cos u − sin Ω·sin u·cos i)
y = r·(sin Ω·cos u + cos Ω·sin u·cos i)
z = r·sin u·sin i
```

Переход к системе координат, связанной с Землёй, при `θ = earth_angle0_deg·π/180 + 2πt/T`:

```text
xₑ = cos θ·x + sin θ·y
yₑ = −sin θ·x + cos θ·y
zₑ = z
```

### 13.2. Наземные и межспутниковые контакты

Координаты наземного пункта широты `φ` и долготы `λ`: `g = R·(cos φ·cos λ, cos φ·sin λ, sin φ)`. Для спутника с земными координатами `s` угол возвышения равен `arcsin(((s − g)·g) / (‖s − g‖·R))`. Результат `arcsin` переводится в градусы. Наземный контакт доступен при угле не меньше `min_elevation_deg` и активном спутнике. Для линии со шлюзом дополнительно учитывается его доступность.

Для двух активных спутников с координатами `a` и `b` контакт доступен при `‖b − a‖ < isl_range_km` и расстоянии от центра Земли до отрезка `[a; b]` больше `R`. Для проверки отрезка: `d = b − a`, `q = clip(−a·d/(d·d), 0, 1)`; ближайшая точка равна `a + qd`. При совпадении координат используется расстояние `‖a‖`.

Контакты двунаправленные. Маршрут начинается в выбранном `client`, проходит через один или несколько активных спутников и заканчивается в доступном `gateway`. Промежуточные узлы маршрута — спутники. Недоступный аппарат сохраняет расчётное положение и исключается из состава связей на период отказа.

Каждый маршрут рассматривается для текущего отсчёта времени. Основные показатели характеризуют геометрическую доступность пути. Расчёт пропускной способности, очередей передачи и задержки ожидания контакта команда может добавить отдельным функционалом.

## 14. Показатели результата

Для каждого наземного пункта рассчитываются:

- доля времени видимости хотя бы одного активного спутника;
- доля времени наличия пути до шлюза;
- максимальная длительность перерыва.

Доли равны числу соответствующих отсчётов, делённому на общее число отсчётов. В интерфейсе они отображаются в процентах.

Максимальный перерыв — самая длинная последовательность отсчётов без пути, умноженная на `step_s`. Перерывы в начале и конце периода учитываются отдельно. Число переходов маршрута равно числу его рёбер и включает две наземные линии. При отсутствии пути значение числа переходов отсутствует.

Показатели выводятся по каждому пункту. Сравнение показывает одинаковый период и принятые изменения конфигурации. Параметры высоты, дальности и угла возвышения сохраняются для сопоставления проектных вариантов; исследование других значений оформляется отдельным запуском с отображением новых условий.

## 15. Работа с расчётным модулем

`geometry.py` содержит функции для расчёта положения аппаратов и контактов. Требования: Python 3.10+, NumPy (`python -m pip install numpy`). Подключение — обычным импортом.

```bash
python "Расчетный модуль/geometry.py" "Данные/01_full_constellation.json" 0
```

Команда выводит состояние сети в нулевой момент. В коде доступны `load(path)` для чтения файла, `validate(scenario)` для проверки входа и `snapshot(scenario, t_s)` для получения состояния. Результат `snapshot` содержит `satellites` с координатами `x_km`, `y_km`, `z_km` и флагом `active`; `edges` со связями `[id_1, id_2, distance_km]`; `elevation_deg` с углами возвышения по наземным пунктам.

Формулы раздела 13 позволяют реализовать те же расчёты на любом языке. Алгоритмы маршрутизации, подбор конфигурации, сравнение проектов и пользовательский интерфейс входят в решение команды.

## 16. Сохранение и выгрузка

Выгружаемый результат содержит:

- `schema_version` со значением `cosmo-A-result-1.0`;
- `effective_scenario` с полным использованным сценарием;
- `routes` со списком маршрутов.

Для каждой пары «момент расчёта — наземный пункт» должна присутствовать одна запись с полями `t_s`, `client_id` и `path`:

```json
{"t_s": 120, "client_id": "C65", "path": []}
```

`path` содержит последовательность идентификаторов от наземного пункта до шлюза; пустой список означает отсутствие построенного маршрута. К результату можно добавить сводные показатели и пояснения. Сохранённые настройки должны включать изменения, выполненные пользователем перед запуском.

## 17. Проверка входа

- Числовые значения конечны, идентификаторы уникальны в соответствующих списках.
- Ссылки на плоскости и аппараты разрешаются.
- Продолжительность и шаг — целые положительные секунды, продолжительность кратна шагу.
- Все интервалы недоступности расположены внутри периода расчёта и имеют положительную длительность.
- При ошибке сервис указывает проблемное поле или объект.

## 19. Глоссарий

| Термин | Определение |
|---|---|
| Спутниковая группировка | Совокупность спутников, совместно обеспечивающих связь. В кейсе — 48 аппаратов в три очереди по 16 |
| Орбитальная плоскость | Плоскость движения группы спутников вокруг Земли. Спутники распределены между несколькими плоскостями |
| RAAN (`raan_deg`) | Ориентация орбитальной плоскости вокруг Земли. Изменение RAAN поворачивает всю плоскость и меняет географию прохождения спутников |
| Фазирование (`phase_deg`) | Общий сдвиг спутников одной плоскости вдоль орбиты. Не поворачивает плоскость, а меняет положение аппаратов на ней |
| Очередь запуска (`launch_batch`) / этап развёртывания (`launch_stage`) | `launch_batch`: этап вывода спутника (1, 2, 3). `launch_stage`: сколько очередей запущено (1 → до 16 аппаратов, 2 → до 32, 3 → все 48) |
| Наземный клиентский пункт (`client`) | Точка, для которой проверяется связь со шлюзом. Не используется как ретранслятор |
| Шлюз (`gateway`) | Целевая наземная станция — выход из спутниковой сети в наземную |
| Угол возвышения (`elevation`) | Угол спутника над горизонтом пункта. Контакт возможен при угле не ниже порога |
| Межспутниковая связь / ISL | Прямая связь между спутниками, если они достаточно близко и линия не перекрыта Землёй |
| Геометрическая видимость | Наличие активного спутника, видимого из пункта. Сама по себе не гарантирует доставку до шлюза |
| Сквозная достижимость / доступность связи | Полный путь «пункт → спутники → шлюз». Доля шагов с таким путём — основной показатель; ориентир ≥ 90% |
| Маршрут | Последовательность связей от пункта через спутники до шлюза в данный момент. Может меняться или исчезать |
| Перерыв связи | Непрерывный период без сквозного маршрута. Максимальный перерыв — самый длинный за горизонт |
| Шаг расчёта | Дискретный момент пересчёта (в базовых сценариях 120 с, горизонт — сутки) |
